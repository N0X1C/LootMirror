# LootMirror — Dev Notes / Progress Log

Read this before making further changes. It captures *why* things are built the way they are, not just *what* — several design decisions here were forced by real bugs found through trial and error in-game (I — Claude — cannot run WoW myself; everything was verified via the user's screenshots, `/fstack` dumps, and chat reports).

Current version: **2.0** (kept at the user's explicit request during Session 5's pre-release review, after briefly trying 2.1 — see Session 5 point 4). Interface: 120100 (WoW 12.1, Midnight).

The user communicates in German; code/comments/commit messages stay in English (matches existing style).

## Status

Addon is feature-complete for its current scope, including a full per-character Wishlist feature (Session 3), a live settings Preview (Session 4), and two review/cleanup passes (Session 2 + Session 3). Options window is a fully custom dark/flat-themed UI (no Blizzard XML templates), scrollable, resizable, with a custom color picker, its own Game Menu → Options → AddOns entry, and now two tabs (Options / Wishlist) in one window. Loot filtering is deliberately narrow: **equipment only**, Poor quality always hidden, no per-item-type toggle — see "Scope decision" below, don't re-add a general item-type filter without re-reading that. Wishlisted items are the one deliberate exception to that filter (see Session 3).

The footer's old one-shot **Test** button is now a **Preview** toggle (Session 4) — see the Session 4 summary below before touching it.

## Scope decision — read this before adding filters

LootMirror is **not** a general loot log. It exists specifically to catch group loot in dungeons/raids and, above all, the loot burst at the end of a Mythic+ run, where Blizzard's own loot display is easy to miss. Two things follow from that, both hardcoded in `ShouldFilterLoot` (Core.lua), not exposed as options:

1. **Equipment only.** Only `Enum.ItemClass` Weapon(2)/Armor(4)/Profession equipment(19) ever show up. Consumables, trade goods, quest items, reagents, etc. are always filtered, unconditionally.
2. **Poor quality is always hidden.** It's never worth flagging and equipment is essentially never Poor quality anyway.

An earlier version of this session added a full "Item Type" filter section (Equipment/Consumable/Trade Goods/Quest/Other checkboxes, mirroring the Quality filter). The user explicitly said this was too much (`"Ich glaube das ist zu viel... Ich brauche keine Filter für die items. Auch das poor kann weg."`) and asked for the simpler hardcoded behavior instead. That section was fully removed again. **Don't re-add a togglable item-type filter unless the user asks for it again** — the hardcoded equipment-only behavior is the intended design, not a placeholder.

**Wishlist items are the one exception**: a wishlisted item's drop always bypasses `ShouldFilterLoot` entirely (equipment-only + quality checks), in both the sync and async paths — see rule 10/16 and Session 3 item 3. The user explicitly asked for items to be tracked "no matter who loots them," and the Adventure Guide (where items get wishlisted from) shows plenty of non-equipment loot too (mounts, patterns, appearance items under "Bonus Loot").

## Hard-won architecture rules — don't undo these without a reason

1. **No legacy Blizzard XML templates in Options.lua.**
   `UIDropDownMenuTemplate`, `OptionsSliderTemplate`, `UIRadioButtonTemplate`, `GameMenuButtonTemplate` are NOT used. The original Options.lua used them and the window silently did nothing (`/lm` toggled nothing) — most likely because on this client one of these templates errors out during creation, which aborts the rest of the Lua file, so `LootMirror.Options.Toggle` and the slash-command handler never got defined. Everything is built from native widget types (`Frame`, `Slider`, `Button`, `EditBox`, `ScrollFrame`) + `BackdropTemplate` (which *is* safe — extremely widely used, not deprecated). The one exception is `UIPanelButtonTemplate`, used only for the "Open Options" button on the Game Menu → AddOns category page (Blizzard's own canvas page, a different context — that template is standard there).

2. **No `Texture:SetGradient`.**
   Confirmed broken on this client: the call doesn't error, but the texture never gets colored. Broke the color picker's SV square/hue bar and the header accent lines. Fixed everywhere by using `SetColorTexture` on many small solid-colored regions instead. Don't use `SetGradient` for anything new.

3. **No Blizzard `ColorPickerFrame` reuse.** Built a fully custom picker instead (SV square + hue bar + New/Prev + Hex) — it's a shared global frame, reskinning it would affect every addon, and its internal structure isn't stable across expansions.

4. **Dropdown menus and the color picker popup are parented to `optFrame`, not `content`.** `content` is the scrollable area's scroll-child; anything popped up from inside it must NOT be a descendant of the ScrollFrame or it gets clipped past the visible viewport. Parented to `optFrame` directly, positioned via `SetPoint` against the triggering widget, with `SetFrameLevel(optFrame:GetFrameLevel() + 50)`.

5. **ScrollFrame's scroll-child needs exactly one anchor + explicit `SetSize`.** Anchoring both TOPLEFT and TOPRIGHT to auto-match width breaks it — the ScrollFrame manages the child's position internally and a second competing anchor fights that. This is now encapsulated in `LootMirror.CreateScrollList` (LootFrame.lua) — see rule 12.

6. **`row:SetPoint()` offsets already get multiplied by the row's own `SetScale()`.** Don't pre-multiply spacing by `scale` in `UpdateRowPositions` — that double-applies it.

7. **Loot bars and the anchor render at `"FULLSCREEN"` strata**, one tier above the Options window's `"DIALOG"` strata (but below `"TOOLTIP"`, so item-compare tooltips stay on top).

8. **`DisplayLoot` in Core.lua is `pcall`-wrapped** (`DisplayLootImpl` is the real body). WoW doesn't print Lua errors to chat unless "Show Lua Errors" is enabled, so an unguarded error here fails completely silently. Keep this wrapper on any future changes to that function. The Wishlist EJ-integration code (Wishlist.lua) follows the same pattern for its own callbacks.

9. **Filtering state (quality + item-class + wishlist bypass) has to be threaded through both the sync AND async paths.** `ShouldFilterLoot(quality, itemClassID)` is called both in `DisplayLootImpl` (item already in client cache) and in the `GET_ITEM_INFO_RECEIVED` handler (item wasn't cached yet at loot time, resolved later). If you add a new filter dimension (or a new bypass), make sure it's checked/threaded in *both* places — see rule 10 and rule 16.

10. **`bypassFilter` (used by `/lm test` and wishlist matches) must be threaded through the pending-item queue too, not just the initial synchronous check.** `RunLootTest` calls `DisplayLoot(..., true, ...)` so Test always fills `Max Loot Bars` regardless of the user's quality filter. A wishlisted item's `isRealWishlistMatch` is folded into the same `bypassFilter` flag before it's stored on the pending entry (`bypassFilter = bypassFilter or isRealWishlistMatch`). If the item isn't cached yet, it goes through `pendingItems` and gets re-checked in `GET_ITEM_INFO_RECEIVED` — that path used to re-apply the normal filter and silently drop the bypass. Fixed by storing the (combined) bypass flag on the pending entry itself and checking `entry.bypassFilter` there too. If you add other one-off entry points that need to skip filtering, follow the same pattern.

11. **Don't add a wrapper function that just calls another function with no added behavior.** `RefreshBarScale` used to duplicate `UpdateRowPositions`'s per-row `SetScale` call, then also call `RefreshLayout` (which does the exact same `SetScale` again). Removed entirely — callers now call `LootMirror.RefreshLayout()` directly, which already re-applies scale *and* spacing *and* position in one pass over `activeRows`.

12. **Shared scrollable-list mechanics live in `LootMirror.CreateScrollList(parent, opts)` (LootFrame.lua).** Options.lua's settings list and Wishlist.lua's item list both call this instead of each hand-rolling their own ScrollFrame + scrollbar track/thumb + wheel/drag handling. It had already drifted once (mismatched wheel-scroll speed, 40 vs 30) before being extracted — if you need a third scrollable area, use this helper, don't copy-paste a fourth implementation.

13. **Never hook Encounter Journal (Adventure Guide) loot-item buttons or GameTooltip's `OnMouseUp`/`OnTooltipSetItem` scripts on this client — both broke it.** Three attempts were made to detect "user is interacting with a loot item in the Adventure Guide" for the Wishlist feature:
    - `hooksecurefunc("EncounterJournal_LootItem_OnClick", ...)` (+ a Mixin-form fallback) — silently never fired for the newer per-dungeon "loot browser" view (Class Filter / All Slots / Mythic dropdown), and was never confirmed to work even for the classic per-boss Loot tab.
    - `GameTooltip:HookScript("OnTooltipSetItem", ...)` installing a per-owner `HookScript("OnMouseUp", ...)` dynamically — caused a live `bad argument #2 to HookScript` error immediately on `/reload` (before any hovering happened), because `HookScript("OnMouseUp", ...)` errors on some frame type encountered in this client's Adventure Guide.
    - **What actually works (current implementation):** no hooking of any Blizzard function/script at all. A lightweight `OnUpdate` — only ever attached while `EncounterJournal` is shown, toggled via `EncounterJournal:HookScript("OnShow"/"OnHide", ...)` — polls `IsMouseButtonDown("RightButton")` for the down-edge. On that edge, if `IsShiftKeyDown()` and `GameTooltip:IsShown()`, it reads the item straight off `GameTooltip:GetItem()`. Pure reads + polling + hooking only the *top-level* EncounterJournal frame's show/hide (safe, same pattern as `optFrame`'s own OnHide hook) — nothing here can break the Encounter Journal, whatever its internal button/tooltip structure looks like. **If more Adventure Guide integration is ever needed, extend this polling approach — do not go back to hooking loot-button clicks or tooltip scripts.**

14. **`EJ_GetCurrentInstance`/`EJ_GetInstanceInfo` do not exist as globals on this client**, and `C_EncounterJournal` (which does exist) has no direct replacement in its listed methods (confirmed via `/run for k in pairs(C_EncounterJournal) do print(k) end`: `GetEncountersOnMap`, `GetLootInfo`/`GetLootInfoByIndex`, `GetSectionInfo`, `GetSlotFilter`/`SetSlotFilter`, `InstanceHasLoot`, `GetBaseDifficultyID`, etc. — no instance-name getter among them). The currently-viewed dungeon/raid name was instead found (via `/fstack`, hovering the breadcrumb bar) to live in the second Adventure Guide breadcrumb button's text: `_G.EncounterJournalNavBarButton2Text:GetText()` (breadcrumb is Home → Instance → deeper drill-down, so button 2 is consistently the instance). This is a plain `FontString:GetText()` read, not a hook — can't break anything, worst case it returns nil (e.g. nothing drilled into yet). If this stops working on a future client update, re-run the `/fstack` diagnostic rather than guessing at more `EJ_*`/`C_EncounterJournal` function names.

15. **`optFrame`'s `OnHide` hook is the single place that closes the anchor bar (`LootMirror.MainFrame`) when the options window closes**, regardless of *how* it closes (× button, Save, or anything else added later). Don't duplicate "also hide MainFrame" logic into individual button `OnClick` handlers again — it drifted once already (only Save did it, so × left the anchor bar stuck open) before being consolidated into the one `OnHide` hook.

16. **Wishlist entries are `{ id = itemID, link = fullItemLink or nil, source = instanceName or nil }`, and matching (`IsWishlisted`) keys ONLY on `id`.** This is intentional, not an oversimplification: the same base itemID can drop at different bonus-ID'd qualities/tracks (Champion/Hero/Myth, upgrade levels, etc. in the current expansion's crest system), and the user explicitly wants "this item, at any level" to match, not one specific bonus-ID combo. `link`/`source` exist purely to make the *management list* display the right quality/icon/dungeon-name — they must never be used for the match check itself. Legacy entries saved as a bare number (pre-Session-3 format) are still read fine via the `EntryID`/`EntryLink`/`EntrySource` helpers at the top of Wishlist.lua, which handle both the old (bare number) and new (table) shapes.

## Session 3 (wishlist feature) summary

Added a full per-character Wishlist feature end-to-end, plus a design pass on the Options window and a review/cleanup pass. Roughly in order:

1. **Data layer** (`Wishlist.lua`, new file) — `LootMirrorCharDB.wishlist` (new `SavedVariablesPerCharacter` in the .toc), an array of `{id, link, source}` entries (see rule 16). `LootMirror.Wishlist.Init/IsWishlisted/GetAll/Add/Remove/RefreshUI` — `Init` is called from Core.lua's `ADDON_LOADED` handler.
2. **Loot-bar highlight** — `LootMirror.SetRowWishlist(row, bool)` in LootFrame.lua overrides the row's border to gold (`WISHLIST_BORDER`) and shows a star badge (`Interface\Common\FavoritesIcon`... actually implemented via atlas `auctionhouse-icon-favorite`), restorable back to the configured border color via `row.lastBorderColor` (stashed by `ApplyColorsToRow`). Applied in `DisplayLootImpl` for **any** group member's drop (highlight is group-wide by explicit user request), independent of who eventually loots it.
3. **Auto-remove on self-loot** — when the wishlisted item is looted by the player *themselves* (`player == UnitName("player")`), it's removed from the wishlist automatically and a chat confirmation is printed (using the item link so it renders as a clickable colored link). Deliberately NOT triggered for a groupmate's pickup — they might roll/hold it for you, and either way you still want your own copy. Also deliberately NOT triggered during `/lm test` (`isTest` param on `DisplayLoot`/`DisplayLootImpl`) — otherwise a player whose character name happens to match one of the test's hardcoded NPC names (Thrall, Jaina, Arthas, ...) could have a real wishlist entry silently deleted just by clicking Test. The rest of the test's other (non-forced) rows still exercise the *real* IsWishlisted match/highlight, just not the removal side-effect.
   - Trading an item to the player was assumed (not confirmed live) to flow through the same `CHAT_MSG_LOOT` "You receive item" self-message as looting, so it should hit this same code path for free — flagged to the user as unverified; ask them to test if it matters.
4. **Wishlist bypasses the loot filter** (see Scope decision above + rule 10) — found in the Session 3 review pass and fixed: previously `ShouldFilterLoot` ran *before* the wishlist check, so a wishlisted non-equipment item or a disabled-quality item would never even get a loot bar.
5. **Adding items** — two entry points:
   - Manual: an input box in the Wishlist tab accepts a pasted item link (Ctrl+V, since shift-click does **not** insert into a custom EditBox — that's chat-editbox-only, confirmed by user testing) or a typed numeric item ID.
   - Adventure Guide: **Shift + Right-click** while hovering a loot item (see rule 13 for the three attempts before landing on the working OnUpdate-polling approach). Shift+**Left**-click was deliberately rejected as the trigger per user request — it's the client's universal "link to chat" gesture, used everywhere else, so repurposing it would be disruptive.
   - Both paths capture the dungeon/raid name via `EncounterJournalNavBarButton2Text:GetText()` (Adventure Guide adds only — manual/pasted entries have no source) — see rule 14.
6. **Merged into one window, tabbed** — the Wishlist UI was originally its own popup window, then merged per user request into the main Options window as a second tab ("Options" / "Wishlist"), sharing title/border/Panel Scale+Opacity/footer buttons (Move Anchor/Test/Save). `LootMirror.Wishlist.BuildUI(container, containerWidth)` is called once by Options.lua, building the wishlist UI inside a tab-panel frame that Options.lua owns and shows/hides (`ShowTab("options"|"wishlist")`).
7. **Shared scrollbar helper extracted** (rule 12) — `LootMirror.CreateScrollList` in LootFrame.lua, used by both the Options tab and the Wishlist tab's item list.
8. **Visual/branding changes** (explicit user requests):
   - Window borders (main window + anchor bar) → solid black, full opacity (`{0,0,0,1}`). Kept as a *separate* palette entry (`C.windowBorder` in Options.lua) from `C.border` (the internal hairline color for dividers/input boxes/swatches, left unchanged/blue-tinted) — the request was specifically about the window edges, not every internal line.
   - Top accent bars (the blue/green two-tone stripe) removed entirely from both the main window and the anchor bar.
   - "LootMirror" title text → blue (`C.accent`/`ANCHOR_ACCENT`) instead of gold, in both places.
   - Close button (×) enlarged twice on request → final: 44×44 hit area, 32px glyph (was 24×24 / default GameFontNormalLarge size).
   - Per-row Wishlist remove (×) button also enlarged → 32×32, 20px glyph (was 20×20 / default size); row height bumped 32→40 and icon 24→28 to fit a second (dungeon/raid source) text line without crowding.
   - Removed the "LootMirror: Loaded. Type /lm for options." login chat message per explicit request.
9. **Review/cleanup pass** (via the `/code-review` skill on the full working-tree diff, then manually verified) — found and fixed: the filter-bypass ordering bug (item 4 above), the `/lm test` name-collision auto-removal bug (item 3 above), and a dead `C.title` palette entry (unused after the title switched to `C.accent`). Also deduplicated the scrollbar code (item 7 above) on explicit follow-up request ("will nichts doppelt haben").
10. **`LootMirror.toc`** — added `Wishlist.lua` to the load order (`LootFrame.lua`, `Wishlist.lua`, `Options.lua`, `Core.lua` — Wishlist before Options since Options calls `LootMirror.Wishlist.BuildUI` at its own load time) and a new `## SavedVariablesPerCharacter: LootMirrorCharDB` line. Version was **not** bumped past 2.0 this session.

## Session 4 (live Preview toggle) summary

User feedback: the footer only had a one-shot **Test** button, so checking a slider/color tweak meant re-clicking Test after every single change. Replaced with a live preview:

1. **Every content-area control now applies live**, not just on Save/Test — same pattern the header's Panel Opacity slider already used (`ApplyPanelOpacity` on every `OnValueChanged` tick). `ApplySettings` (Options.lua) is now forward-declared (`local ApplySettings` before the content section, then `function ApplySettings() ... end`, no `local`, at its real definition further down) specifically so the slider/dropdown/checkbox/color-swatch closures created *before* that point can still see it as an upvalue instead of resolving to a global `nil`. Sliders are hooked directly (`slider:HookScript("OnValueChanged", LiveApply)`); dropdown/checkbox/color-swatch factories (`CreateModernDropdown`/`CreateQualityCheckbox`/`CreateColorSwatchRow`) gained an optional trailing `onChange` callback parameter (also `LiveApply`), fired from each widget's own click/drag handler, since those factories only return a `{GetValue/SetValue}`-style wrapper table, not the underlying interactive frame, so there was nothing to `HookScript` from outside.
2. **Test button → Preview toggle.** `LootMirror.RunTest()` (still used by `/lm test`, unchanged) spawns rows that auto-expire after `duration`, which doesn't work for "leave it on screen while I drag sliders." Added `LootMirror.StartPreview()`/`LootMirror.StopPreview()` (Core.lua) instead: same `DEMO_POOL` item list (extracted as a shared module-level local so `/lm test` and Preview don't duplicate it), spawned via a new `noExpire` param threaded through `DisplayLoot`/`DisplayLootImpl` that skips the row's `C_Timer.After` auto-release and instead tracks it in a new `previewRows` list for `StopPreview` to release explicitly. The footer button toggles between the two, and `optFrame`'s `OnHide` gained a second hook (kept separate from the existing rule-15 one, which already closes the anchor bar) that force-stops an active preview when the window closes any way (×, Save, Escape) — otherwise the demo rows would linger after Options closes.
3. **Double-release guard:** if a real loot event fires while Preview is active and trims `activeRows` past `maxRows`, the evicted row is now also stripped from `previewRows` at that point (in `DisplayLootImpl`'s maxRows-trim block) — otherwise `StopPreview` would later call `LootMirror.ReleaseRow` on that same row a second time (it was already released once by the trim), corrupting the row pool. Follow the same pattern if another code path is added that can evict a preview row out from under `StopPreview`.
4. **`suppressLiveApply` guard (bug found by the user, fixed same session):** the user reported settings resetting every `/reload`. Root cause: `ApplySettings()` unconditionally reads *every* control's current value, but `optFrame`'s `OnShow` restores those controls from `LootMirrorDB` one `SetValue`/`SetColor`/`SetChecked` call at a time. With live-apply wired straight to `ApplySettings`, each slider's restore call fired mid-sequence and wrote the *other*, not-yet-restored controls' stale values back over the DB — since color swatches/checkboxes/dropdowns are restored last and don't themselves trigger a re-apply, `borderColor`/`bgColor`/`filterQuality` ended up permanently overwritten with stale values the moment Options was opened after a reload. Fixed with a module-level `suppressLiveApply` flag (Options.lua): every live-apply call site goes through a small `LiveApply()` wrapper that no-ops while the flag is true, and `OnShow` sets it true at the start of its restoration block and false at the end. **If you add another control whose value gets restored in `OnShow`, make sure its live-apply hook goes through `LiveApply`, not a direct `ApplySettings()` call** — a direct call would reintroduce this same bug for that control.
5. **Live-verified**, unlike most other features in this file — the user tested this one immediately (see the `suppressLiveApply` bug above) rather than only reasoning about it from the code, so treat the Preview toggle itself (rows appearing/staying up/clearing correctly) as working unless they report otherwise.

## Session 5 (pre-release review) summary

User asked for a full review before uploading to CurseForge. Ran the `/code-review` skill (high effort) across the whole codebase, not just the working diff, then fixed what it found and did a manual pass for release/packaging concerns:

1. **`classCache` pollution from demo rows (found by review, fixed):** `RunLootTest`/`StartPreview` (`/lm test` and the Preview toggle) seed `classCache[name]` with hardcoded colors for their fake NPC names (Thrall=Shaman, Jaina=Mage, ...) so the demo rows show a real class color, but never restored it — so if a real player in your group is literally named e.g. "Thrall", running Test/Preview would permanently mis-color their real loot rows afterward (`GetClassColor` only does a live lookup on a cache miss, so a stale cached entry sticks until the next `GROUP_ROSTER_UPDATE`). This is the same class of name-collision risk already guarded against for wishlist auto-removal (`isTest`, Session 3) but the class-color seeding was never given an equivalent fix. Fixed with `SeedDemoClassCache`/`RestoreDemoClassCache` (Core.lua): every seed now snapshots and restores the prior value (nil if there wasn't one) once the demo rows are done reading it -- immediately after the loop for `StartPreview` (synchronous, no stagger), or via a `C_Timer.After(count * 0.3 + 0.1, ...)` for `RunLootTest` (rows are staggered, so restoring has to wait for the last one). **If you add another place that seeds `classCache` for display purposes, pair it with a restore the same way** — don't leave a demo/preview seed in the shared cache permanently.
2. **Color picker SV-grid over-repaint (found by review, fixed):** `RepaintSVGrid` (Options.lua) recomputes all 980 SV-square cells via `SetColorTexture` every time `RefreshColorPopup` runs — which happens on every `OnUpdate` tick while dragging *either* the hue bar *or* the SV square, even though the grid's cell colors only depend on hue, not on the S/V marker position. Dragging inside the SV square was repainting the whole grid every frame for zero visual change. Fixed with a `lastPaintedHue` guard that no-ops the repaint when hue hasn't actually changed since the last paint.
3. **Wishlist.lua button styling duplication (found by review, not fixed — left as-is):** `Wishlist.lua`'s Add/Remove buttons hand-roll their own backdrop/hover-color logic instead of reusing Options.lua's `CreateModernButton` pattern, so a future visual tweak to that shared look could silently drift out of sync between the two files (the same drift risk rule 12's `CreateScrollList` extraction was meant to prevent, just for buttons instead of scrollbars this time). Not fixed this session — `CreateModernButton` is a local function in Options.lua, so reusing it would mean exposing it via the `LootMirror` namespace and touching both files right before a release, which felt like unnecessary risk for a purely cosmetic-maintainability issue. Worth doing in a calmer moment, not urgent.
4. **README pass; version left at 2.0.** `LootMirror.toc` was briefly bumped 2.0 → 2.1 (neither the Session 3 wishlist feature nor Session 4's live-preview work had ever bumped it), but the user explicitly asked to set it back to 2.0 right after -- **don't re-bump it without being asked again.** README.md was still updated to document the Wishlist feature and the Preview toggle (previously only covered Session 2's changes) — see its Wishlist section and the updated Options/Files sections; that part stands regardless of the version number.
5. **Reviewed and ruled out** (no changes needed): SavedVariables defaulting is consistently `or {}`/`or default`-guarded at every read site, including Options.lua's file-load-time code which runs before Core.lua's `ADDON_LOADED` handler in the `.toc` load order. No `SetGradient`/legacy-XML-template violations were reintroduced (rules 1/2). The Encounter Journal integration (rule 13/14) still doesn't hook anything and stays `pcall`-wrapped. The wishlist filter-bypass is still correctly threaded through both the sync and async (`GET_ITEM_INFO_RECEIVED`) paths (rule 9/10). No taint-prone calls on secure/protected frames. No debug `print`/`TODO`/leftover-test artifacts in the shipped code — every `print` is an intentional user-facing chat message.
